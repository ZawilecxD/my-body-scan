# PRD: My Body Scan

A personal body map plus injury log. Not a camera scan, not a medical product.

## 1. Problem & Users

Tracking a physical issue needs three things at once: **where** it is, **whether it is still current**, and **what to do about it**. A notes app has no body. A clinical/physio app is heavy, account-based, and aimed at a clinic.

**Primary user (MVP):** Mateusz — the builder and first production user, who has injuries to track now.

**Later users (do not expand MVP for them):** anyone tracking body problems, especially sportspeople and people working with a physio.

**Why now:** those injuries exist today; the missing middle is a schematic body map + status log.

## 2. Goals & Non-Goals

### Goals

- **G1.** On one Android device, the user can attach an injury to a coarse body landmark via the graphic or via the grouped list, and see it again after restarting the app.
- **G2.** Open injuries are distinguishable from healed ones without opening the archive; each open injury shows its latest proposed solutions (text and links).
- **G3.** Archiving an injury removes it from the current/open views and leaves it readable in the archive.
- **G4.** A second person can be walked through the three core journeys without a missing-screen apology (graphic front/back, list, close-up, injury thread, archive).

### Non-goals

- iOS
- Camera, photo, or any real body scan
- 3D, medical-grade anatomy, or picking individual muscle fibers
- Built-in exercise catalog
- Accounts, cloud sync, backup, or export
- Sharing with a physio or any multi-user flow
- Diagnosis, AI advice, treatment recommendations generated by the app, or presenting as a medical device

## 3. Core User Journeys

### J1 — Log an injury from the body map

Open the app → body graphic (front). Toggle to back if needed. Tap a region (head, torso, arms, legs) → close-up of that region's landmarks. Tap a landmark (e.g. forearm, elbow) → create an injury: description carries any extra specificity; optional proposed solutions as text + http(s) links. Return to the map; that landmark shows as having an open injury.

### J2 — Follow current status (list or map)

Toggle to the **list** (first-class, grouped by body part) **or** stay on the graphic. See only **open** injuries. Open one → read description, chronological comments, and proposed solutions. Add a comment and/or another solution link (usually YouTube). The point of this journey: what is wrong now, and how it is being dealt with.

### J3 — Archive when healed, find it later

On an open injury, archive it as healed. It disappears from current/open map markers and from the open list. Open the archive, find that injury, read its history. It cannot be lost; it is no longer "current."

## 4. Functional Requirements

### Views & navigation

- **FR-1.** The user can switch between two equally available views: **body graphic** and **list grouped by region**. Neither is hidden in settings.
- **FR-2.** On the graphic, the user can toggle **front** and **back**.
- **FR-3.** The graphic shows four tappable regions: head, torso, arms, legs. Tapping a region opens that region's close-up for the current side (front or back).
- **FR-4.** Each close-up shows only the MVP landmarks for that region × side (catalog in §5). Landmarks are schematic tap targets, not an atlas.
- **FR-5.** Tapping a landmark starts **create injury** on that landmark, or opens the existing open injury/injuries on it.
- **FR-6.** The list view groups **open** injuries by region and shows the landmark name; tapping a row opens that injury.
- **FR-7.** Landmarks with at least one open injury are visually marked on the graphic (region overview and close-up).
- **FR-8.** Archive is a separate screen listing archived injuries; the user can open any of them read-plus-history (comments and solutions remain visible).

### Injuries

- **FR-9.** An injury is always attached to exactly one landmark. Specificity beyond the landmark lives in the description (forearm muscle → forearm; something around the elbow → elbow + text).
- **FR-10.** Creating an injury requires a description. Solutions are optional at create time.
- **FR-11.** A proposed solution is user-authored **text** plus an optional **http(s) URL**. There is no exercise picker.
- **FR-12.** The user can add solutions to an existing open injury after creation.
- **FR-13.** The user can add timestamped comments to an open injury. Comments form a chronological thread (oldest first).
- **FR-14.** An injury is either **open** or **archived**. There is no other status flag in MVP.
- **FR-15.** Archiving is an explicit user action on an open injury. Archived injuries do not appear in the open list or as open markers.
- **FR-16.** The user can reopen an archived injury (move it back to open) from the archive. (Needed so a "healed then flared" problem does not require a duplicate; if this is dropped, archive is write-once.)
- **FR-17.** Tapping a solution URL leaves the app via the system handler (browser or YouTube). The app does not embed video.
- **FR-18.** All of the above data survives process death and app restart on the same device.

### Explicit non-behavior

- **FR-19.** The app does not interpret symptoms, suggest exercises, or score pain. It stores what the user typed.
- **FR-20.** First launch does not require an account, email, or network.

**FR-16 default:** reopen is in. It is the cheap way to handle a flare-up without a second injury on the same landmark. Call it out in review if you want archive to be one-way.

## 5. Data & Domain

```
Region 1──* Landmark 1──* Injury 1──* Comment
                              └──* Solution
```

| Entity | Meaning |
|---|---|
| **Region** | One of: `head`, `torso`, `arms`, `legs`. Navigation only. |
| **Side** | `front` \| `back`. A landmark exists on a region × side. |
| **Landmark** | Coarse tap target (forearm, elbow). Not a medical muscle name. Catalog below is the MVP contract. |
| **Injury** | A problem attached to one landmark. `description` (required), `status` (`open` \| `archived`), `created_at`, `archived_at` (set when archived, cleared if reopened). |
| **Comment** | Timestamped text on one injury. Ordered by time ascending. |
| **Solution** | User text + optional `url` on one injury. Not a catalog item. |

No User entity in MVP (single on-device owner).

### MVP landmark catalog

Schematic names. Same idea on left/right limbs — **one target per pair** (not separate left/right tap targets). Description can say "left."

**Head / front:** skull, jaw, neck  
**Head / back:** skull, neck  

**Torso / front:** collarbone, chest, ribs, abdomen  
**Torso / back:** upper back, lower back  

**Arms / front:** shoulder, upper arm, elbow, forearm, wrist, hand  
**Arms / back:** shoulder, upper arm, elbow, forearm, wrist, hand  

**Legs / front:** hip, thigh, knee, shin, ankle, foot  
**Legs / back:** glute, hamstring, knee, calf, ankle, foot  

MVP may **trim** this list; it must not grow. Left/right split is out (description handles it).

## 6. External Interfaces

No product backend, no auth provider, no analytics, no YouTube API.

The only external interaction: open a user-supplied `http` or `https` URL with the Android system handler. Invalid or empty URLs are not opened.

## 7. Non-Functional Requirements

- **Platform:** Android only. Phone-sized screens are the design target; tablet layouts are not required.
- **Storage:** On-device only. Injury data is not transmitted by the app. Opening a URL is the user's action, not a data export.
- **Offline:** Every journey except **FR-17** works with no network.
- **Durability:** Data still present after force-stop and reboot.
- **Quality bar:** Showable — both views, front/back, close-ups, injury thread, archive, all reachable without placeholder screens.
- **Map quality:** Schematic is enough. Tap targets must be large enough to hit; the list view is the accessible alternative to the graphic.
- **Safety:** Copy must not claim diagnosis or treatment. This is a personal tracker.

## 8. Success Metrics

Personal MVP — no telemetry. Success is checked by hand:

| Metric | Pass |
|---|---|
| **M1. Real log** | Builder has every *current* injury in the app, each on a landmark, with whatever solutions they actually use. |
| **M2. Demo loop** | A second person can complete J1–J3 in one sitting without a missing screen or "imagine this" step. |
| **M3. Status split** | After archiving, the open list and map markers match "what's current"; the archive still shows the healed item. |
| **M4. Offline** | J1–J3 (except opening a YouTube link) work in airplane mode, then still work after restart. |

## 9. Risks & Open Questions

### Risks

- **R1.** The schematic map is still confusing. **Mitigation already in the product:** coarse landmarks + description; list view is first-class.
- **R2.** The catalog is too coarse (everything lands on "knee") or too busy. **Mitigation:** trim-only catalog; do not add left/right or muscle-fiber targets.
- **R3.** A showable bar plus custom art stalls the MVP. **Mitigation:** art is schematic; list view ships even if the graphic is ugly. Illustration *source* is a stack/implementation choice, not a product one.

### Open questions

- Trim the §5 catalog before build? (Do not expand.)
- **FR-16** reopen vs one-way archive — default is reopen.
- Later (not MVP): export/backup, iOS, left/right landmarks, physio sharing.
